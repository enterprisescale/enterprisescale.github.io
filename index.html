The Mental Model Shift: From Lakehouse to Operational Platform

A data engineer's transition to Palantir Foundry: how the Ontology shifts the paradigm.

If your background is in Snowflake, Databricks, dbt, or a modern cloud data stack, your first instinct when approaching Palantir Foundry is to treat it as a bundled lakehouse. You see PySpark transforms, incremental datasets, branch controls, and pipeline graphs, and you assume: “this is just managed Spark with a nice UI.”

That assumption holds up right until it doesn't. In a standard data stack, data flows in one direction: source, ingest, transform, dashboard. Pipelines are read-heavy analytical engines, and the last mile is a human looking at a chart.

Foundry is built around a bi-directional operational loop spanning two distinct tiers. Data flows down into an operational layer, applications and agents mutate state in that layer, and those mutations flow back into files. Once you internalize the loop, most of the platform's “weird” behavior becomes obvious.

01 The core abstraction: datasets vs. the Ontology

To build effectively in Foundry, you must separate platform storage into two tiers.

  • Tier 1 The dataset layer. A dataset is a wrapper around a collection of files in a backing filesystem — a self-hosted HDFS cluster or cloud storage such as Amazon S3 — with Foundry maintaining the mapping from logical to physical path. Structured datasets hold tabular files, typically Parquet, plus column metadata. Versioning is by transaction: SNAPSHOT, APPEND, UPDATE, and DELETE, each an atomic change analogous to a Git commit (Palantir: Datasets).
  • Tier 2 The Ontology. The operational layer of the enterprise. It contains semantic elements (objects, properties, links) and kinetic elements (actions, functions, dynamic security), and it is backed by multiple services in a microservices architecture — not a single database (Ontology overview, Ontology architecture).
  • Object Storage v2 (OSv2). The object database that indexes and serves ontology data — a component of the Ontology, not a synonym for it. Funnel converts merged rows into index files stored in a separate index dataset; OSv2 then downloads those index files onto the disks of its search nodes, a step called hydration (Funnel batch pipelines). It serves low-latency reads, search-arounds, and aggregations through a Spark-based query execution layer.
Key rule for engineers

User-facing operational applications (Workshop) and AIP agents read through the Ontology, not the raw dataset layer. The file-facing tools sit on the other side: Contour performs point-and-click analysis on tables at scale (Contour), Pipeline Builder is Foundry's primary data-integration application and, with Code Repositories, the main dataset-producing surface (Pipeline Builder), and Code Workspaces brings JupyterLab, RStudio Workbench, and VS Code onto the same datasets, Iceberg tables, and virtual tables (Code Workspaces). Foundry SQL is the one surface that deliberately spans both tiers — SQL Studio queries datasets, tables, and ontology object types through a common Spark SQL dialect (SQL in Foundry).

Tooling note

If a tutorial you are following reaches for Code Workbook, check its lifecycle banner first: it is “in the legacy phase of development, and no additional development is expected,” with full support retained and other applications recommended instead (Code Workbook). For large-scale transformation work use Pipeline Builder or Code Repositories.

Terminology note

Older documentation and blog posts reference OSv1, codenamed Phonograph. It entered planned deprecation and was scheduled to become unavailable after June 30, 2026, so treat OSv2 as the backend you will actually encounter (Object Storage v1).

Why transaction type decides your pipeline's fate

Append-only history is what enables efficient incremental computation. An APPEND adds new files and cannot modify existing ones; an UPDATE may overwrite the contents of existing files, which breaks the append-only requirement and forces downstream consumers back to full SNAPSHOT processing. Pick a tab to see what each transaction does to the current dataset view.

02 Reading and writing: idiomatic incremental transforms

In pure append-only transforms, added output rows are a function only of newly added input rows. Changing column types, formatting dates as strings, and filtering all qualify. The only difference required to make such a transform incremental is the incremental() decoration — nothing else in the function body changes (Incremental transforms: examples).

Python append_only.py 
from transforms.api import transform, incremental, Input, Output

# Append-only: the added output rows are a function of the added input rows.
@incremental()
@transform(
    students=Input('/examples/students_hair_eye_color'),
    processed=Output('/examples/hair_eye_color_processed'),
)
def incremental_filter(students, processed):
    new_students_df = students.dataframe()
    processed.write_dataframe(
        new_students_df.filter(new_students_df.hair == 'Brown')
    )

When you need to compare against previously computed state (Example: an upstream system sends overlapping batches to avoid data loss over network blips), you leave append-only territory and move to the merge and append pattern, which the docs introduce with a precise phrase: sometimes a transform needs to refer to its previous output in order to incrementally compute an update. The default input read mode is added, which returns only rows appended since the prior build in an incremental run — but cleanly falls back to returning the entire dataset in a non-incremental run, because every row then counts as unseen (Incremental transforms reference).

Python merge_and_append.py 
from transforms.api import transform, incremental, Input, Output

# Merge and append: dedupe incoming rows against the previous output.
@incremental(semantic_version=1, v2_semantics=True)
@transform(
    source_data=Input('/path/to/incoming_raw_dataset'),
    processed_data=Output('/path/to/incremental_output_dataset'),
)
def compute(source_data, processed_data):
    # 'added' returns newly appended rows in an incremental run,
    # or the entire dataset when running non-incrementally (all rows unseen).
    new_df = source_data.dataframe()

    # Dedupe against the previous output. Passing a schema handles the
    # initial non-incremental run, where 'previous' is empty.
    delta_df = new_df.distinct().subtract(
        processed_data.dataframe('previous', schema=new_df.schema)
    )

    # Incremental run  -> default write mode is 'modify' (append).
    # Non-incremental  -> default write mode is 'replace'.
    processed_data.write_dataframe(delta_df)
Schema caveat

Deduplication via .subtract() compares the input DataFrame against the output DataFrame, so it requires the two schemas to match. If your transform maps fields, casts types, or otherwise alters schema, append your transformed added rows directly instead of subtracting.

The reason the same function body works in both execution modes is that the default modes are designed to pair up. Read this table once and most incremental surprises stop being surprises.

Mode Incremental run Non-incremental run
added input default Rows appended since the transform last ran The entire dataset — all rows are considered unseen
previous output read The DataFrame produced by the last build An empty DataFrame — pass schema= so it can be constructed
current The entire input for this run The entire input for this run
modify write default (incremental) write_dataframe() appends to the existing output Not the default — replace applies instead
replace write default (snapshot) Only if set explicitly via set_mode() Fully replaces the output with what this build wrote

Modes and defaults per the incremental transforms reference. The decorator itself takes require_incremental, semantic_version, snapshot_inputs, allow_retention, strict_append, and v2_semantics; Palantir recommends all users set v2_semantics=True (API reference).

03 The writeback loop: how Actions actually persist

This is the part that breaks the lakehouse model outright. A user clicks a button in a Workshop app, or an AIP agent invokes an Action, and a record changes — yet no Spark job ran and nothing in your pipeline's build graph moved. Here is what actually happened, in order.

The consequence worth internalizing: all indexed data in object databases is ephemeral. The durable copy of your ontology state is the datasource plus the Funnel-owned merged dataset — not the index that served the read. Persistence is still the file layer's job, which is exactly why the two tiers stay coupled by a loop rather than a one-way pipeline.

Consistency tradeoff

Under OSv2 the Actions service only version-checks objects directly used to generate edits. This reduces StaleObject conflicts, but the guarantee is genuinely weaker: objects read during an Action without being edited are not guaranteed to have stayed unchanged for the duration of the apply. If your Action derives one object's value from another, that read is not protected the way an OSv1 cross-check would have been. In database terms, OSv1 targeted Serializable isolation (read-set validation), whereas OSv2 operates like Snapshot Isolation (write-set validation)—preventing shared reference objects from causing cascading transaction aborts across the enterprise.

Where to look when you need forensics

Because the merged datasets are owned and managed internally by Funnel, they never appear in your pipeline's build graph. That is a visibility boundary, not a missing audit trail — you just have to use the right tool.

  • Dependencies and downstream impact: Workflow Lineage manages workflows built on top of the Ontology and can show all downstream usages for a specific column in an object, including dependent actions and Workshop applications (Workflow Lineage). Data Lineage covers the end-to-end path from source to Ontology to workflow, and object types can be added to the lineage graph directly (Data Lineage).
  • Operational writes: the Action log models action submissions as object types, one log object type per action type, all prefixed [LOG]. Each submission creates a single log object automatically linked to every object the action edited, capturing action RID, action type version, timestamp, user ID, and the primary keys of edited objects. It is opt-in and configured per action type — for function-backed action types the backing Ontology edit function must have Edits provenance configured. If you want a record of every edit regardless of action, enable edit history on the object type instead (Action log).
Takeaway:

Datasets provide immutable historical storage, while the Ontology serves as the transactional, write-capable layer that application logic and agents interact with directly.
