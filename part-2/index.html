Correcting History Without Burning the House Down

Part 1 covered why Foundry isn't just a lakehouse. This one covers what happens when the data flowing through that operational loop turns out to be wrong — and why the warehouse reflex of "patch the code, overwrite the table" picks the wrong tool most of the time.

Where part 1 left off

Foundry's dataset layer isn't the last mile: it feeds a live, queryable Ontology that Workshop apps and agents read and write through continuously — the two-tier model, plus the Actions writeback loop, covered in Part 1: The Mental Model Shift. Everything below assumes that second tier exists.

A pipeline can fail mid-run, a transform's logic can be subtly incorrect, a source system can emit bad values for weeks before anyone notices, or a bad write can duplicate a day of history. Each of these calls for a different fix, and the warehouse reflex doesn't distinguish between them; applied to the wrong one, it either under-corrects the data or stalls the operational loop.

This post walks through a decision ladder covering the tradeoffs across these scenarios. Read it end to end for the full picture, or jump directly to the rung matching your own situation. A single running example — three weeks of bad data that went undetected in production — threads through the walkthrough to keep the tradeoffs concrete, but the ladder itself generalizes past that one case.

01The 30,000-foot lakehouse baseline

In a traditional cloud warehouse (Snowflake, Databricks, BigQuery), the table under the bug is a stateless analytics view. The standard fix is a full INSERT OVERWRITE: recompute the table from raw data with the corrected code and commit a new version. On Iceberg or Delta this doesn't even discard history — it commits a new snapshot, and prior snapshots stay addressable until they expire. This works because the last mile is a dashboard or a batch job that queries periodically. Swapping the table underneath costs compute time, not uptime.

Foundry's dataset layer looks similar on the surface — transactions, snapshots, incremental reads. The difference is what sits downstream of it: the dataset isn't the last mile. It feeds a live, queryable Ontology that Workshop apps and agents read and write through continuously. That second tier is why the warehouse reflex needs to be replaced, not just ported over.

02Step 0: find the bad transaction before you touch anything

Before choosing a remediation, scope the damage. Foundry's Time Travel (beta) in Dataset Preview is built for exactly this: it lets you inspect a dataset or Iceberg table across its committed versions, diff a range for added/removed/modified rows against a key column, and run Bisect to search version history for the first commit where a specific cell value changed.

Two limits matter here: Bisect only searches versions already loaded on the page, and it can only inspect versions still available under the dataset's retention policy. If the bad transaction fell outside retention, you're scoping by date range and downstream lineage instead of a precise bisect. Once you know which transaction and how many rows, you're ready for the actual decision.

Practitioner call

The mechanics cited throughout this ladder — Funnel's pipeline stages, edit-queue behavior, schema-migration rules — are drawn directly from Palantir's documentation and community threads, linked inline. The ladder that organizes them into a decision path is my own mental model for navigating the tradeoffs, not an official Palantir framework.

03The decision ladder

The choice of remediation depends on where the problem originates: the pipeline's own execution, or the data it was fed. Answer the two or three questions below and the ladder resolves to a single rung — or click any node directly to see the path of decisions that reaches it.

04Rung 1 — did the meaning of the transform change, or just its output?

Once you've ruled out a pipeline-execution issue (that's Rung 4 — a duplicate run, a bad write, a job that just needs to reproduce correct output with the existing or now-fixed pipeline), this is the next fork.

Semantic break → hard reset

The logic or semantics changed

A join key was wrong, a filter excluded the wrong population, the business definition of a field changed. The historical rows were never valid under any interpretation.

Value break → backfill

The intent was right, a bug corrupted values

A cast overflowed, a null-handling branch was missing, a formula had a sign error. The fix is a value correction on a known set of rows.

The second case is more common in practice; the first applies specifically when the transform's definition itself needs to change.

05Rung 2 — the semantic_version hard reset

Foundry's @incremental() decorator accepts a semantic_version argument specifically for this. Raising it forces the next run to be non-incremental: previous comes back empty, the transform is presented the full input as if for the first time, and the default output write mode switches to replace — a full rewrite of the output (Incremental transforms usage guide).

This is the right tool when the transform's definition changed and every historical row needs to be recomputed under the new definition — Palantir's own guidance is to review semantic_version whenever an input or logic change "fundamentally changes the semantics of the transform." It is the wrong tool when only a subset of rows in a fixed window are wrong, because a full replace rewrites 100% of the output regardless of how small the actual damage was.

A semantic_version bump rewrites 100% of the output, so it almost always crosses that line — which is exactly why it should be reserved for genuine semantic breaks, not value-level bugs. It functions as a last resort — not because it carries inherent risk, but because it's disproportionate to a value-level bug.

python transforms/orders.py 
@incremental(semantic_version=2)
@transform_df(...)
def compute_orders(raw_orders):
    # Runs non-incrementally exactly once: raw_orders is the full input,
    # previous is empty, and the output is written with mode='replace'.
    return transformed_df

06The hard reset vs. the invisible edits

Rung 2 raises an obvious follow-up: while your semantic_version bump was rewriting six months of history, operators were still using the Ontology — clicking Actions in Workshop, correcting records by hand. What happens to those edits when the baseline underneath them gets replaced wholesale?

Three mechanics answer that. Open the ones you need.

User edits are never written into your pipeline's own output dataset. When an Action fires, the Actions service sends a modification instruction to Funnel, which stores it in an offset-tracked queue, applies it immediately to the live OSv2 index (so reads are consistent right away), and only later flushes it into a separate, Funnel-owned merged dataset that combines datasource rows with user edits — a dataset that never appears in your pipeline's build graph (How user edits are applied). Your semantic_version reset rewrites the dataset you own; it does not touch that separate edit queue at all.

Every Funnel batch pipeline — incremental or full-reindex — runs the same four stages: changelog, merge changes, indexing, hydration. The merge-changes step is where "all changelog datasets from the changelog step and any recent user edits coming from Actions are joined by the object type's primary key to merge all changes" (Funnel batch pipelines). That step doesn't change based on whether the trigger was a normal incremental update or a semantic_version full rewrite — the freshly recomputed baseline still gets merged against the same live edit queue by primary key. A hard reset doesn't blow away six months of Workshop edits by mechanism; it recomputes the baseline those edits get layered onto, using the object type's configured conflict-resolution strategy per property.

That merge is keyed strictly on primary key value, and the underlying risk isn't unique to Foundry: in a lakehouse, changing how a table's join or primary key is generated is also a breaking change for every downstream consumer's contract, since anything joining on that key silently stops matching. Foundry adds an edit-specific consequence on top of that shared risk, worth separating by how well-documented each is:

  • Reassigning which property serves as the primary key is a documented breaking schema change. On Object Storage v1, "user edits cannot be migrated" through this change and are lost outright absent a "time-consuming and complex manual intervention." On Object Storage v2, the schema migration framework provides predefined migrations for other breaking changes, but "the framework does not support applying migration instructions on the primary key property of object types" — Palantir does not document a supported path for carrying edits through a primary-key reassignment (Manage schema changes).
  • Leaving the schema alone but changing how the existing primary-key column's values are computed (new hashing logic, a new surrogate-key sequence, a case-sensitivity fix) isn't a documented "schema change" — this is inference from the PK-keyed identity model, not a quoted platform guarantee. The old key values disappear from the datasource, which the default conflict strategy treats the same as a deleted row (permanently, even if a matching row "reappears" later under the old key), and the new key values arrive as brand-new objects with no edit history attached.

Stop-and-test signal

If your remediation touches primary-key generation logic at all, treat that as a stop-and-test-in-a-lower-environment signal — it's the one failure mode neither a backfill nor a hard reset can recover from after the fact.

07The conflict-resolution knob, precisely

Foundry lets you configure, per input datasource, how a property's pipeline-driven value is reconciled against a standing user edit, in the object type's Datasources section in Ontology Manager (Conflict resolution strategies). The second strategy has a trap in it that the table alone doesn't convey — so try it.

Property ownership: what belongs to the pipeline vs. the Ontology

A related question an incident like this should provoke: should an operational application even be editing a property the pipeline also writes? A normal, dataset-backed property is meant to originate from the pipeline, with edits layered on top via the conflict-resolution strategy above. An edit-only property, by contrast, has "no mapping to a column in the backing dataset" and exists for values "that will only be edited through the ontology" (Edit-only properties) — and edits to it "always apply," regardless of conflict-resolution strategy or any Timestamp comparison (How user edits are applied).

Practitioner call

Practically: if a value is inherently operational — an assigned reviewer, a manually-set status flag — and no pipeline will ever compute it, model it as edit-only, so a future backfill or hard reset can never touch it in the first place. If a value is inherently pipeline-computed and an operator edit is meant as an exception, not the norm, keep it a normal property under an explicit conflict-resolution strategy rather than leaving the default unexamined.

08How teams manage the reindex window

The mechanism here is documented; the duration isn't. Hydration — "downloading the index files from the dataset into the disks of the OSv2 database search nodes" — is Palantir's own term for the final step of a Funnel batch pipeline, but Palantir doesn't publish a duration figure for it (Funnel batch pipelines). For the specific case where a full reindex also requires a replacement pipeline — which Palantir documents today for object-type schema changes — the read-availability answer is explicit: "while the live pipeline continues to run on its usual cadence, Funnel will orchestrate a replacement pipeline in the background without impacting the live data being served to users," and only "after the replacement pipeline successfully runs for the first time" does it take over (same source). That's a background build with an atomic cutover, not a blackout window for readers.

Two separate guarantees are at play here, from two different pages. Funnel's replacement-pipeline behavior, above, is about read continuity — queries keep working while the rebuild happens in the background. Separately, Palantir's edit-consistency guarantee states that "if an object read occurring as part of an ontology query happens after a user modification is sent, the object read is guaranteed to contain the user edits" — with no stated exception for a rebuild window.

One environment, one object type: a semantic_version bump reindexed the live pipeline in-place rather than provisioning a replacement pipeline. Reads kept returning pre-bump values for the entire changelog-to-hydration cycle — no errors, no downtime, just pre-bump counts until the process finished. Separately, edits submitted mid-cycle (during indexing and during hydration) were reflected immediately in SQL Console, consistent with Palantir's documented edit-consistency guarantee, which states no exception for a rebuild window (How user edits are applied). Neither page documents the mechanism behind that — whether writes land on the still-live old index while queued edits apply on top until cutover — but the outcome held. One data point, not a guarantee it generalizes; validate in a lower environment for your own object types.

Funnel's documented performance heuristic can automatically provision a replacement pipeline "for performance reasons based on various heuristics" Palantir doesn't enumerate, so a different object type, data volume, or Foundry instance could fall on the other side of that same heuristic and behave differently. Validate the reindex window for your own object types in a lower environment rather than assuming this result generalizes.

Which trigger routes to which mechanism

Palantir's documentation doesn't specify which mechanism a manual trigger uses. Testing in one Foundry instance observed a replacement pipeline being provisioned, with the object type remaining queryable via SQL Console throughout — consistent with the documented replacement-pipeline read-continuity guarantee, though replacement pipeline not confirmed as universal behavior across Foundry versions or configurations.

09A note on concurrent writes during long rebuilds

One more caveat worth flagging: the "no impact on live data" language above is specifically about reads continuing to serve from the still-live pipeline during the background build. Neither this page nor any other Palantir page states what happens to concurrent writes — Actions/user edits — while a replacement pipeline is running in the background. That's not a documented guarantee either way.

A relevant real-world account comes from a developer forum thread on replacement pipeline mechanics, where a practitioner reports a replacement pipeline that "takes around 10-12 hours to run fully" for a streaming-backed object — confirming these windows can run well past a single working session, not minutes.

Mechanically, the replacement pipeline almost certainly incorporates the edit queue's contents at some point via its own Merge changes step — Palantir documents that "any recent user edits coming from Actions" get joined into the merge changes dataset as a step every Funnel batch pipeline runs through, and a replacement pipeline is described as "an entirely new Funnel pipeline" (Funnel batch pipelines).

What's not clear is whether it stays continuously in sync with new writes throughout that 10-12 hour build, right up to cutover, or whether it merges once early on and leaves later edits to be picked up in a subsequent cycle. Recall from Part 1 that Funnel's edit queue flushes on a six-hour cadence; a replacement pipeline running longer than six hours raises the question of whether it gets its own independent catch-up cycle, or whether the queue simply won't flush against it until it catches up.

Working hypothesis

Since Funnel's edit queue already uses offset tracking, it's plausible the replacement pipeline tracks its own offset and Funnel holds off flushing until it catches up — but that's bordering on speculation; Palantir's docs don't describe this mechanism for replacement pipelines specifically.

This is exactly the kind of gap that can turn into a real production incident. One documented case shows both the live and replacement pipelines getting stuck in failure-backoff states simultaneously, requiring manual intervention to resolve (Limits on vector embeddings in Ontology) — a concrete example of what can go wrong when a replacement pipeline doesn't complete cleanly (in that case, due to compute resource limits rather than write volume, but the failure mode — two pipelines stuck, needing intervention — illustrates the risk).

Practitioner call

Because the exact mechanics of this catch-up phase aren't published, multi-hour replacement pipelines carry an unquantified risk of catch-up stalls or failure-backoff loops if write velocity is high during the build. A reasonable mitigation is validating long rebuild windows empirically, or scheduling schema-change-driven rebuilds during low-write or no-write operational windows.

And that's before accounting for the schema-change case specifically: the same developer forum thread that confirmed the 10-12 hour build window also reported that after the schema change went live, "a number of OSDK based apps failing since they couldn't load the objects" because deleted properties were no longer queryable — a concrete instance of a hard reset via schema change breaking consuming applications during exactly this kind of extended reindex (Ontology replacement pipeline mechanics).

10Rung 3 — if it's a value break: how big is the affected slice?

This is where the two backfill patterns diverge, and the choice is really about ownership and scale, not correctness — both are correct.

Option A: the auxiliary replay dataset

Build a permanent secondary input — the auxiliary replay dataset — alongside the main pipeline. When a bug is found, deploy the fixed code, then append the three weeks of original raw (uncorrupted-at-source) records into the auxiliary dataset. Because both inputs are read in added mode, the pipeline unions the auxiliary dataset's new rows with the day's normal delta, runs both through the now-fixed logic, and appends the corrected results to the output. On the next run, the auxiliary dataset's added view is empty again — no truncate, no rollback, no lingering special-case code path.

Two constraints, both enforced by Object Storage v2's sync semantics rather than style preference:

  • The auxiliary replay dataset must always receive APPEND transactions, never a SNAPSHOT. A SNAPSHOT load fully rewrites the auxiliary dataset's contents, which breaks the main transform's ability to run incrementally on that input at all — the exact fate this pattern exists to avoid.
  • You must deduplicate to one row per primary key before the write if the replay window overlaps today's normal delta. OSv2 requires that "each transaction must contain, at most, one row per primary key," using a "most recent transaction wins" rule (Funnel batch pipelines).

The dedup gotcha

Order the ranking window by the source's business/event timestamp (e.g. updated_at) — never by a runtime timestamp such as current_timestamp(). The auxiliary dataset's replayed rows carry an old business timestamp from three weeks ago; a runtime timestamp would instead reflect when the replay job happened to run, which could make a three-week-old replayed value look newer than today's genuine update and win the rank arbitrarily.

python transforms/orders_replay.py 
from transforms.api import transform, incremental, Input, Output
from pyspark.sql import Window
import pyspark.sql.functions as F

@incremental()
@transform(
    main_input=Input("/Enterprise/Landing/Raw/orders_landing_stream"),
    replay_input=Input("/Enterprise/Operations/ReplayDatasets/orders_replay_aux"),
    processed_output=Output("/Enterprise/Ontology/Backing/orders_clean"),
)
def compute_orders(main_input, replay_input, processed_output):
    normal_delta_df = main_input.dataframe('added')
    replay_delta_df = replay_input.dataframe('added')
    combined_raw_df = normal_delta_df.unionByName(replay_delta_df)
    transformed_df = apply_fixed_business_logic(combined_raw_df)

    # Mandatory OSv2 rule: at most one row per primary key per transaction.
    # Order by source business timestamp, not runtime, so today's real update wins.
    window_spec = Window.partitionBy("order_id").orderBy(F.col("source_event_time").desc())
    deduped_output_df = (
        transformed_df
        .withColumn("row_rank", F.row_number().over(window_spec))
        .filter(F.col("row_rank") == 1)
        .drop("row_rank")
    )
    processed_output.write_dataframe(deduped_output_df)

Option B: hash-diff CDC (self-healing backfill)

Load the full snapshot of source data every run, apply the current transformation to every row, hash the resulting payload, and compare it against a deduplicated view of the previous output. When a code fix changes a row's hash, the pipeline detects the discrepancy on its own and emits the delta as an APPEND. This is genuinely idempotent — running it twice against unchanged inputs and code produces an empty delta both times — and it requires no manual replay injection; it will catch the next silent regression too, not just this one.

The cost is compute: every row in the source is recomputed on every run before the delta is even calculated. There's also a specific join-mechanics trap worth seeing rather than reading about.

python transforms/orders_cdc.py 
from transforms.api import transform, incremental, Input, Output
from pyspark.sql import Window
import pyspark.sql.functions as F

@incremental()
@transform(
    raw_snapshot=Input("/Enterprise/Landing/Raw/orders_snapshot"),
    processed_output=Output("/Enterprise/Ontology/Backing/orders_clean"),
)
def compute_orders_cdc(raw_snapshot, processed_output):
    current_df = apply_fixed_business_logic(raw_snapshot.dataframe())
    payload_cols = [c for c in current_df.columns if c not in ("order_id", "source_event_time")]
    # sha2 over a 32-bit hash reduces collision risk at high row counts
    current_state_df = current_df.withColumn(
        "row_hash", F.sha2(F.concat_ws("||", *payload_cols), 256)
    )

    raw_previous_df = processed_output.dataframe('previous', schema=current_state_df.schema)
    window_spec = Window.partitionBy("order_id").orderBy(F.col("source_event_time").desc())
    latest_previous_df = (
        raw_previous_df
        .withColumn("row_rank", F.row_number().over(window_spec))
        .filter(F.col("row_rank") == 1)
        .select("order_id", F.col("row_hash").alias("prev_hash"))
    )

    diff_df = current_state_df.join(latest_previous_df, on="order_id", how="left")
    delta_df = diff_df.filter(
        F.col("prev_hash").isNull() | (F.col("row_hash") != F.col("prev_hash"))
    ).drop("prev_hash")
    processed_output.write_dataframe(delta_df)

11Rung 4 — when is a literal rollback actually justified?

Sometimes the entire output for a window needs to disappear, not be corrected. Foundry's dataset rollback exists for this. Used within its documented limits, it is a legitimate remediation tool. Drag the rollback point below to see what it does and doesn't revert.

  • Rollback does not, by itself, reset incremental state or force a snapshot. Palantir states plainly that "if the dataset is being built incrementally, the dataset rollback feature also ensures that the incrementality of your dataset is preserved" (Roll back a dataset). Forcing a snapshot is a separate, deliberately chosen action in the same tool — not a side effect of rolling back.
  • The real cost is on the Ontology side, and it's manual, not automatic. The same page states: "If a dataset backs an object type stored using Object Storage v2, manual intervention is required to ensure that the object type is reindexed with a successful run of the replacement pipeline to reflect the state after the rollback."
  • It has real limits. You can only roll back to a successful transaction, not one removed by a retention policy; rollback doesn't revert logic changes if the code changed since that transaction; and pipeline-level rollback is in planned deprecation, capped at 50 transactions, in favor of per-dataset rollback.

Rollback is the right call when the output itself should never have existed — e.g., an errant job wrote to the wrong branch — not when the output is directionally right but numerically wrong on a subset of rows. For the latter, a backfill leaves the operational loop running; a rollback plus manual reindex does not.

Does the next build have to re-fetch everything from the source? No. Rollback only reverts the output dataset you targeted — Palantir describes it as updating "the data and job history of a dataset," not its inputs. Your upstream sources are untouched, so the next scheduled incremental run reads previous as the rolled-back state and reprocesses the input rows added since that point. One caveat Palantir states plainly: "the logic backing the dataset will be left unchanged and will need to be updated in order to apply to the next build" (Roll back a dataset) — rollback reverts data, not code.
