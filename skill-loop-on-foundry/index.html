A Skill Loop for Foundry, One Component at a Time

Twelve components, built one at a time, each one added because something went wrong or something was not allowed. The starting point is a Google Research paper that runs tasks to improve an agent's skills. I turned it around to run agents that improve a code base, inside a platform where production is off limits. This is the shape the loop ended up with, and where it departs from the paper.

The use-case here stands in for the real one. A team receives contract documents under a master services agreement and has to map each one to the obligations it creates. Invoices and other files are matched to obligation types by deterministic patterns, with an LLM fallback for the ones the patterns miss. Every few weeks someone asks for a new pattern type, and supporting it means touching a TypeScript repo, a Python/Spark pipeline, and a few business rules about how dates in a filename are read. That recurring request is what I built the loop around.

The tooling is Palantir's. The skills run inside AI FDE, which operates Foundry through natural language, works in a loop of execute, observe, decide, and by default proposes changes on a branch as a Global Branch proposal or a pull request rather than writing to main. The paper is WikiSkill, from Tang and colleagues at Google Research, August 2026.

01 The loop, as a play

Twelve boxes in two bands. Nothing moves; each beat adds boxes and connections to a layout that is already final, so by the end you have watched the design assemble in the order I actually built it. Press play or step through. Once the play ends, each box is clickable and explains what it does.

02 The paper's loop

WikiSkill keeps three layers on disk: raw/ with immutable execution traces, wiki/ which compiles those traces into pattern pages, a log and a skill-impact.md tracker, and skills/ with the active skill set (Tang et al.). Each iteration runs the agent on a batch of tasks, samples up to eight traces, updates the wiki, and asks a Skill Proposer for one atomic change to one skill. The change stays only if the validation score strictly improves; otherwise the skill set reverts and the rejection is recorded so it is not proposed again. The wiki is never rolled back.

Two details turned out to matter for me. The agent doing the work does not read the wiki during rollouts; when the authors tried giving it access, average performance dropped from 63.7% to 60.9% (Tang et al.). And the whole apparatus exists to improve the skill. Task outputs are there for scoring; the skill set is what carries over.

03 The inversion

My tasks are not a benchmark. They are real requests, and the output is the point. So my first mapping onto Foundry kept the part the paper only uses for measurement, the task run and its output, and skipped the part the paper optimises, the skill edits. Two skills: an implementation skill that makes the code change on a global branch, and an acceptance skill that tests it independently and returns PASS, FAIL or BLOCKED. The proposal was the deliverable. Improving the skills could wait until there was something to learn from.

AI FDE proposes changes as a Global Branch proposal or a pull request by default and asks for explicit approval before mutating operations; file edits and dataset builds are auto-approved on feature branches but not on protected ones (Palantir docs). I leaned on that default: the loop works on branches and a person merges.

04 Four incidents

Four things went wrong in the first runs, and each one turned into a rule. Commits landed on the branch from outside the loop, so now the loop stops on branch-state drift until the re-checks pass. One runtime could not validate both the Python and the TypeScript repo; that became the BLOCKED outcome, with a person deciding what happens next. The implementation skill noticed that normalisation differed between the generator and the consumer and asked whether that was in scope; it was, and scope expansion became a pause. A pattern I had specified as yearless got a year added by a test case; I ruled that it is always yearless, and conflicting requirements became a pause.

Four more pauses went in without an incident behind them: production mutation, merge or deployment, an unexpected extra resource, and any proposed change to a semantic version or to historical data. The last is a standing rule rather than a lesson. Three of the four were suggested by the agent while I was writing the list.

05 One plan, one approval

Approving every worker call separately meant one pause per step, so I added an orchestrator skill to own the sequence: implementation, acceptance, cross-runtime acceptance, unmerged proposal. I approve that plan once and am interrupted only by the pause list. Two choices here follow the paper's finding that the worker did better without wiki access. Workers never talk to each other; the orchestrator hands each one a delta, not the whole history. And the loop's own memory, a state record written after every accepted transition and before every pause, is visible only to the orchestrator. The last record of each loop holds the run's numbers: iterations to PASS, blocks, rulings, repairs, time to proposal.

06 Ask before building

The yearless incident came down to a requirement I had not stated, not to the code. In the paper every task comes with an answer key, so the question never comes up. A real request arrives with some of its requirements unstated. So a contract builder skill became the first thing a request meets. It reads the wiki, asks the questions that are missing, resolves ambiguous policy, and writes the contract the acceptance skill will test against, including which runtimes have to show which evidence. What gets settled there does not come back later as a pause.

07 Versions everywhere

Once I was editing skills by hand between runs, I could no longer trace a change in behaviour to a change in skill text. Every skill now carries a version and every edit bumps it. The plan pins the versions it was approved against, the state record stores them, and the orchestrator checks for version drift at each worker call, next to branch drift. I treat both as the same condition: the inputs changed after the plan was approved. The paper gets the same thing by recording a unified diff per accepted proposal; I used versions because several skills change independently.

08 The paper, reattached

With runs producing numbers and skills carrying versions, I could attach the paper's loop again, this time around the build loop rather than in place of it. Three pieces. A strengthener skill does the Skill Proposer's job: it reads the wiki, the current skill text, and a bounded bundle of applied changes, past assessments and rejected proposals, and writes proposals that say what effect they expect on the run numbers and which numbers must not get worse. A parent-only change log does what skill-impact.md does: the orchestrator records every proposal, my decision and edits, and the exact version transition. An impact evaluator stands in for the validation gate: read-only, versioned on its own, it compares expected with actual across comparable runs and recommends whether to call the strengthener, wait, do nothing, or look into a regression.

I departed from the paper in three places on purpose. The gate only advises; I apply every skill change myself, as a separately approved edit outside the run that prompted it. The proposer has to predict its effect before the measurement, which the paper's proposer is not asked to do. And only the two worker skills, implementation and acceptance, are ever proposal targets; the orchestrator, contract builder, evaluator and strengthener are edited by people. That is the paper's split between a fixed harness and an evolving skill set, in a system where the harness is also made of skills.

09 Where it stands

All twelve components exist and six real requests have gone through the build loop. There are no comparable runs yet, so I have nothing to say about the strengthener. The number I am watching is time from request to unmerged proposal, across requests. If it does not come down over the next several runs, I will cut the learn loop back. I will add a results section when there is something to report.

One known limit. The loop is single-operator. Its state lives in a per-loop notepad written only by the orchestrator, which is fine until two loops run at once or a pause outlives a session. For concurrent use the state would move to an Ontology object with an Action per transition, which would also give me the audit trail. I have not made that change; nothing has needed it yet.

One thing I checked before building any of this. Palantir's AIP Evolve coordinates fleets of AI FDE agents to improve an AI system against a validation strategy (Palantir announcements). Its unit of work is an AI system and an evaluation; mine is a controlled engineering change across several Foundry resources. Different jobs, so I did not use it.

10 Six loops in

Six real requests in. None of this is a result; it is what kept coming up.

Wiki drafts came back in a different shape every loop. I added an outline and a size cap; by loop six the cap held and the outline had drifted again. A payload 150 characters over its limit also stopped a run outright. Formats are now checked at the boundary, with a tolerance band instead of a hard cap.

Verifier calls take roughly 60 to 70 percent of a loop and I could not cut them: the worker's environment failed differently each time, wrong profile, wrong branch, a workspace that could not run Spark tests. I am adding an environment-readiness check before the first write rather than removing a verifier.

Handoffs shrank by about half, under one rule: every safety fact, evidence item and instruction has to stay recoverable from one canonical place. The loop felt a lot faster; I have not measured that. How well the orchestrator followed the handoff schema also varied with the model running it, which was not the model that wrote its instructions.

Contract defects cause pauses that did not need to happen. The contract builder generates the contract, and one contract had seven defects in it, from a pre-write check that could not be satisfied to a wiki binding the worker was not allowed to use. All seven went into the wiki so they are not argued over again, which is the job the paper gives it.

Solutions over-fit. One change was fitted to the single file pattern in hand. A September 2026 preprint on self-improving review loops notes that the generalisation judgement cannot be made mechanically and is left to a reviewer, bounded by the checks that can be (Wahi). The contract builder's generalisation gate works the same way: it raises the cases a solution should cover with the requester, or at least prompts for that conversation, before the contract is fixed. An abstraction review then sits before acceptance.

Loop maintenance has not ended. It has moved.

11 A side note on the job

Before this, improving the pattern matching meant working on the pattern matching. Now it is three layers: improve the function anyway; automate the process that improves it; instrument that process well enough to improve the process. Only the first changes the code base on the day. Whether the other two pay off depends on the request continuing to recur, which is what the time-to-proposal number is for.

Similar descriptions appear under the name harness engineering on Hacker News, in r/ExperiencedDevs, and on the Stack Overflow blog. Most of that is about a single code base and a coding agent on a developer's machine. I have seen less written about doing it inside a governed platform, with a list of things the loop may never do and a list of reasons it is allowed to stop and ask. It overlaps with what several companies now call the forward deployed engineer role, a title associated with Palantir and since adopted elsewhere with varying definitions.
